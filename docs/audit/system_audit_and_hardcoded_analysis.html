🔍 Category A: Hardcoded Elements & Environment Fallbacks

High Priority

1. Decentralized Gateway Fallbacks Across 18+ Frontend API Modules

Critical Fragility
Every API client module across frontend/src/features/*/api/*.ts individually declares gatewayUrl = import.meta.env.VITE_API_GATEWAY_URL || 'http://localhost:8080'. There is no centralized configuration adapter. If Vercel or cloud environment variables are missed, the browser silently attempts HTTP calls to http://localhost:8080, causing silent network drops (ERR_CONNECTION_REFUSED) or mixed-content HTTPS security blocks.
// Affects 18+ files including: // frontend/src/features/customer/api/delivery.ts:247 // frontend/src/features/courier/api/status.ts:79 // frontend/src/features/merchant/api/webhooks.ts:200 gatewayUrl = import.meta.env.VITE_API_GATEWAY_URL || 'http://localhost:8080'
Remediation: Create frontend/src/config/env.ts as the single source of truth. Validate required variables at application bootstrap; in production, fail-fast with a graceful error toast instead of silent localhost degradation.

2. Hardcoded Port Inconsistency in Pricing Database Fallback

Medium Severity
In services/pricing-service/src/main/resources/application.yml, the database fallback is hardcoded to port 5439 (jdbc:postgresql://127.0.0.1:5439/pricing_db). In contrast, accounts-service, delivery-service, and communications-service use fail-fast syntax without default URLs. If PRICING_DB_URL is omitted, pricing-service silently tries port 5439 instead of failing fast.
# services/pricing-service/src/main/resources/application.yml:34 url: ${PRICING_DB_URL:jdbc:postgresql://127.0.0.1:5439/pricing_db}
Remediation: Standardize on url: ${PRICING_DB_URL} matching the fail-closed pattern of sibling services.

3. Helm Charts Ingress Bound to swiftdrop.local

Medium Severity
Helm chart values files (values.yaml, values-test.yaml) specify host: swiftdrop.local, app.swiftdrop.local, and api.swiftdrop.local. Running Helm deployment directly without passing an environment-specific override produces an ingress unreachable from external public domains.
# platform/kubernetes/helm/swiftdrop/values.yaml:22-27 host: swiftdrop.local app: app.swiftdrop.local api: api.swiftdrop.local auth: auth.swiftdrop.local
Remediation: Parameterize Helm ingress hostnames with mandatory CLI values or dedicated values-production.yaml.

🐞 Category B: Functional Bugs & Edge-Case Vulnerabilities

Critical Impact

1. CI/CD Main Branch Push Trigger Omission

Root Cause Identified
In .github/workflows/ci.yml, the push event trigger is restricted solely to the test branch: push: branches: [test]. When pull requests merge into main, GitHub Actions deliberately ignores the push, preventing verification, GHCR image builds, and automated downstream triggers. This is why backend deployments never trigger automatically after merges to main.
# .github/workflows/ci.yml:4-9 on: pull_request: branches: [test, main] push: branches: [test] # <-- BUG: 'main' is absent! workflow_dispatch:
Remediation: Update push.branches to include both [test, main], and ensure GHCR publish steps accept releases produced from main.

2. API Gateway Dual-CORS Preflight Collision on Comma-Separated Origins

High Severity
Spring Cloud Gateway YAML specifies allowed-origins: [ "${CORS_ALLOWED_ORIGIN:http://localhost:5173}" ] while Spring Security SecurityConfig.java defines a programmatic CorsConfigurationSource that splits by commas. When CORS_ALLOWED_ORIGIN holds multiple origins (e.g. https://swiftdrop-frontend.vercel.app,http://localhost:3000), Spring Cloud Gateway's YAML filter checks for the literal comma-delimited string, rejecting browser preflight requests.
# services/api-gateway/src/main/resources/application.yml:19-21 globalcors: cors-configurations: '[/**]': allowed-origins: - "${CORS_ALLOWED_ORIGIN:http://localhost:5173}"
Remediation: Remove duplicate GlobalCors configuration from application.yml and allow Spring Security WebFlux's CorsConfigurationSource to manage CORS uniformly across all endpoints.

3. GraphQL Service Downstream gRPC Properties Undefined in Config

Medium Severity
services/graphql-query-service/src/main/resources/application.yml omits declarations for swiftdrop.grpc.accounts-target and swiftdrop.grpc.delivery-target. In GrpcClientConfig.java, beans are conditional on property existence. If absent from container environment, the service boots cleanly but all dashboard resolvers crash at invocation time with UNAVAILABLE: Service provider unavailable.
// GrpcClientConfig.java @Bean(destroyMethod = "close") @ConditionalOnProperty(name = "swiftdrop.grpc.accounts-target") AuthenticatedReadClients accountsReadClients(...)
Remediation: Add explicit placeholder declarations with defaults or clear documentation in application.yml.

🏗️ Category C: Architectural & Performance Gaps

Needs Refinement

1. Inconsistent Database Connection Pooling & Missing Timeout Safeguards

Performance & Stability
delivery-service and pricing-service configure maximum-pool-size: 10 and connection-timeout: 5000. However, accounts-service and communications-service omit Hikari settings entirely, falling back to Hikari defaults (30s timeout). When deployed on managed databases with connection pooling (e.g. Supabase), connection spikes can exhaust backend slots or hang threads for 30 seconds.
Remediation: Standardize Hikari pool configurations: maximum-pool-size: 10, minimum-idle: 2, connection-timeout: 5000, and leak-detection-threshold: 20000 across all four database-backed services.

2. In-Memory Gateway Rate Limiting Lacks Distributed Coordination

Scalability Limitation
The API Gateway enforces rate limiting using InMemoryRateLimiter (JVM memory token bucket). If the Gateway is scaled horizontally across multiple pods or VMs, each instance tracks its own bucket, allowing a client to multiply its quota by the replica count.
Remediation: For multi-node cloud production, implement Spring Cloud Gateway's RedisRateLimiter backed by a shared Redis cache.

3. AI Assistant Chat Endpoint is Synchronous & Blocking

UX & Latency
POST /api/v1/assistant/chat executes multi-turn LLM reasoning and internal tool invocations synchronously over HTTP. During peak load, requests hold HTTP worker threads for 4 to 8 seconds.
Remediation: Implement an SSE (Server-Sent Events) streaming response endpoint (GET /api/v1/assistant/stream) or chunked response streaming for token-by-token rendering.

🚀 Category D: DevOps, CI/CD & Deployment Improvements

Operations

1. Absence of Automated CD Pipeline for Azure VM Staging

Operational Bottleneck
Currently, backend updates merged into main require manual SSH login and command execution (git pull && ./start.sh). The staging-promotion.yml workflow only performs dry-run Helm validation locally and does not deploy.
Remediation: Create .github/workflows/cd-deploy-azure.yml triggered on push to main that securely connects via SSH to the Azure VM and triggers rolling service restarts using GitHub encrypted secrets.

2. Docker Container Security & Non-Root Execution: Verified Compliant

Security Achievement
Audit of all 9 Dockerfiles (frontend, keycloak, api-gateway, accounts, pricing, delivery, communications, graphql, ai-assistant) confirms that 100% of services run under dedicated unprivileged users (USER swiftdrop:swiftdrop or nginx-unprivileged). No containers execute as root.
