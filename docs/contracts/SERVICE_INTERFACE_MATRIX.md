## 1. Overview & Purpose

This document provides a single, authoritative reference matrix defining every cross-service synchronous and asynchronous integration boundary across the SwiftDrop microservice platform.

Each interface specification details:
1. **Producer / Service Owner:** The microservice responsible for implementing and serving the endpoint or publishing the event.
2. **Consumer / Service Owner:** The client, service, or worker that calls the endpoint or ingests the event.
3. **Transport Protocol & Identifier:** REST route, gRPC method, Kafka topic/event, GraphQL query, or SSE stream.
4. **Authentication & Authorization:** Credential type, cryptographic verification point, and tenant/role confinement.
5. **Data Ownership & Persistence:** Which PostgreSQL schema or service database is authoritative.
6. **Failure & Timeout Semantics:** Deadlines, circuit breaking, idempotency, retry behavior.
7. **Contract Artifact & Version:** Link to versioned OpenAPI, Protobuf, GraphQL SDL, or JSON Schema artifact.
8. **Implementing Issue & Freeze Status:** Linked November 10 development issue.

## 3. Boundary & Invariant Rules

1. **No Shared Database Access:** Each service is the sole reader and writer of its dedicated database (`accounts_db`, `pricing_db`, `delivery_db`, `communications_db`). Zero cross-service database credentials or foreign keys.
2. **Synchronous Private Communication:** All inter-service synchronous calls strictly use gRPC with Protocol Buffers v3. REST is not used for private internal calls; GraphQL never calls internal databases directly.
3. **Asynchronous Reliability:** Domain events are committed atomically via the Transactional Outbox pattern in Delivery Operations. Kafka KRaft delivers events with at-least-once semantics; consumers deduplicate using `CONSUMED_EVENTS` inbox tables.
4. **Zero Secrets in Events:** Kafka payloads, public tracking endpoints, and application logs strictly omit recipient contact details, passwords, bearer tokens, and private proof-of-delivery object keys.
