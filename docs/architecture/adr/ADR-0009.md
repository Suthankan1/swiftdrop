# ADR-0009: Email OTP Verification Strategy for SwiftDrop

**Status:** PROPOSED — AWAITING SECURITY/PRODUCT APPROVAL · **Baseline:** SwiftDrop v1.3 · **Date:** 2026-10-19 · **Issue:** [Refs #47 (Phase C)](https://github.com/Suthankan1/swiftdrop/issues/47)

---

## Context

SwiftDrop's November 1 deliverable requires a secure, production-grade identity architecture supporting self-registration, user authentication, role-based authorization, and account security.

During the delivery of Issue #47, the platform team verified:
1. **Phase A (PR #48):** Native Keycloak email verification via 256-bit signed action links (`VerifyEmailActionTokenHandler`), backed by Mailpit SMTP, 60s cooldown, and branded Devarom theme.
2. **Phase B (PR #49):** Native RFC 6238 Authenticator-App TOTP multi-factor authentication, including unenrolled pass-through, branded dark-mode QR setup, replay protection, and administrative recovery.
3. **Security E2E (PR #50, PR #51):** 40 automated edge and service verification tests proving JWT rejection (L06), role confinement (L07), and resource-owner isolation (L08).

Phase C evaluates whether to introduce **typed Email One-Time Password (OTP) codes** (e.g., 6-digit numeric codes sent via email) into SwiftDrop's Keycloak platform.

---

## Evaluated Use Cases

We evaluated three separate use cases for typed Email OTP:
- **Use Case A (Signup Verification):** Typing a code vs. clicking the native verification link. Finding: Degrades entropy from $\ge 256$ bits (cryptographically signed JWT action token) to 20 bits ($10^6$ combinations); introduces online brute-force risk without providing stronger proof of mailbox ownership.
- **Use Case B (Second-Factor Authentication / MFA):** Emailed code following password authentication. Finding: Violates factor independence under NIST SP 800-63B §5.1.3.3 due to fate sharing with email-based password reset; unencrypted transit across intermediate MTAs; susceptible to Adversary-in-the-Middle (AiTM) phishing; introduces severe delivery latency/race conditions and transforms SMTP outages into total authentication outages. RFC 6238 TOTP is vastly superior.
- **Use Case C (Account Recovery / Step-Up):** Emailed code for high-risk actions. Finding: Emailed codes provide insufficient assurance for privileged actions (merchant payout, admin roles). Existing administrative reset (`configure-totp.py reset-user`) satisfies operational needs.

---

## Keycloak 26.8.1 Engine Findings

1. **Absence of Native Support:** Keycloak 26.8.1 (Quarkus runtime) **does NOT provide native out-of-the-box support for Email OTP**. Keycloak's core `OTPPolicy` applies exclusively to RFC 6238 TOTP and RFC 4226 HOTP (app/hardware tokens).
2. **Upstream Status:** Community requests for native email OTP (e.g., GitHub Discussion #36910) remain outside Keycloak core scope. Official guidance directs teams to community or custom SPI extensions.
3. **Extension Approaches:**
   - *Third-Party Extensions (Option C):* Third-party JARs introduce severe supply chain risks, lack formal security audits, lag behind Keycloak security patches, and break during Quarkus runtime upgrades.
   - *Custom Authenticator SPI (Option D):* High ongoing Java maintenance burden, requiring bespoke rate-limiting, session-binding, and FreeMarker theme code.

---

## Decision

### Primary Decision: OUTCOME A (Adopted Recommendation)
**Do NOT implement typed Email OTP codes for the November 1 deliverable. Retain Keycloak's native signed email verification links (PR #48) and native RFC 6238 Authenticator-App TOTP (PR #49).**

1. **Email Ownership Verification:** Retain Keycloak's native `VERIFY_EMAIL` action tokens.
2. **Multi-Factor Authentication:** Retain Keycloak's native RFC 6238 Authenticator-App TOTP (`login-otp.ftl`), which operates entirely offline on the user's mobile device, enforces strict single-use replay prevention, and maintains true out-of-band factor independence.
3. **Zero Bespoke Code:** Avoid deploying unreviewed third-party plugins or building custom Java Authenticator SPIs into Keycloak.

### Contingency Specification: OUTCOME C (If Formally Mandated)
If product management or external security stakeholders formally mandate typed email codes for customer onboarding or as an optional MFA fallback:
- That work **must NOT be executed under Issue #47**.
- A separate implementation issue must be opened to build an in-house Keycloak SPI (`DevaromEmailOtpAuthenticatorFactory`).
- The implementation must strictly adhere to the technical invariants specified in [EMAIL_OTP_THREAT_MODEL.md](../../security/EMAIL_OTP_THREAT_MODEL.md) (CSPRNG, 180s expiry, max 3 attempts, 60s cooldown, salted HMAC session binding, atomic burn-on-read, zero secret logging).
- The SPI must undergo independent peer security review prior to deployment.

---

## Alternatives & Trade-Offs

| Alternative | Security Assessment | Operational & Upgrade Impact | Selected? |
|---|---|---|---|
| **Option A:** Native Links + App TOTP | **Strongest.** True factor independence; 256-bit signed tokens; offline MFA. | Zero custom code; zero maintenance; zero upgrade risk. | **YES (Recommended)** |
| **Option B:** Native Keycloak Email OTP | N/A | Feature does not exist in Keycloak 26.8.1. | **No (Infeasible)** |
| **Option C:** Third-Party Plugin JAR | **Weak.** Unvetted supply chain; unknown audit posture; theme conflicts. | High breakage risk on Keycloak minor version updates. | **NO (Rejected)** |
| **Option D:** Custom In-House SPI | **Moderate.** Audited code, but fate-sharing and SMTP DoS risks remain. | Requires building/maintaining ~600 lines Java + theme integration. | **Contingency only (Deferred)** |

---

## Consequences & Security Invariants Preserved

1. **Architectural Stability:** Preserves Keycloak 26.8.1 clean core Quarkus container with zero external JARs.
2. **Availability & Reliability:** User logins do not depend on external SMTP provider latency, reputation warming, or delivery outages.
3. **Factor Independence:** Adheres to NIST SP 800-63B guidelines; avoids fate sharing between password reset and MFA.
4. **Boundary Integrity:** Zero OTP verification in React SPA; zero OTP secrets in Accounts PostgreSQL; zero unauthenticated Gateway endpoints.
5. **Theme Consistency:** Fully preserves SwiftDrop's custom branded FreeMarker login theme (`platform/identity/themes/devarom/login/`).
